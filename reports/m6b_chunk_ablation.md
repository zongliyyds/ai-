## 四、结论与归因（数据驱动，负结果如实记录）

### 1. 粒度：细粒度 vs 基线 vs 粗粒度

- **V2 细粒度 h3/300/前缀(字段)**：chunks 1703（V1 1321）、R@5 0.7833（**-0.0333**）、MRR 0.6931（**-0.0168**）、平均块长 146（V1 190）。
- **V3 粗粒度 整篇/1500/前缀(字段)**：chunks 262（V1 1321）、R@5 0.8500（**+0.0333**）、MRR 0.7656（**+0.0557**）、平均块长 1016（V1 190）。

### 2. 前缀：它到底参不参与检索？

- **V4（无前缀）**：R@5 0.8167（**+0.0000**）；其「检索文本指纹」与 V1 **完全相同**。
  → 说明 `prefix` 字段当前**只进展示、不进检索信号**（FTS tokens 与向量都只取 `text`），「元数据前缀注入」此前是一个**未被兑现的设计意图**。
- **V5（前缀入检索）**：R@5 0.9167（**+0.1000**）、MRR 0.8311（**+0.1212**）；hard 档 R@5 0.5833 → 0.7917。

### 3. 组合验证：两个正增益因子能否叠加？

- **V6（粗粒度 + 前缀入检索）**：chunks 262、平均块长 1093、R@5 0.8333（**+0.0167**）、MRR 0.8132（**+0.1033**）、nDCG@10 0.8261、hard R@5 0.5833。
- 对照：仅粗粒度 V3 R@5 0.8500、仅前缀 V5 R@5 0.9167 → 叠加无额外增益（取两者更强的一方即可）。

### 4. 根因：为什么「前缀入检索」值这么多？——它暴露了分块的真实缺陷

- 现行分块以 `## 标题` 作**分隔符**切块，标题文本随之**被剥离出正文**（正文块里并没有「## 背景」这几个字）；而标题此前只写进 `prefix` 字段，该字段**不参与 FTS tokens 与向量**，section 也只用于展示。
- 后果：「裸标题查询」（hard 档，如 `## 背景 是什么？`）在正文里**找不到任何字面锚点** —— 这正是 M6 中查询改写（E3）与标题重排（E4）都救不回来的根因：问题不在查询侧，而在**索引侧丢掉了标题**。
- 证据：V5 把「文档标题 + 章节标题 + 标签」真正注入块文本后，hard 档 R@5 0.5833 → 0.7917（**+0.2083**）、easy 0.9722 → 1.0000。**增益不是靠题面含文档名**（hard 档题面恰恰不含文档名），而是块文本补回了标题信号。

### 5. 已上线（V5 前缀入检索已于 2026-09-20 采纳）

- 证据最强的两项：①**前缀并入索引文本**（`prefix_mode=inline`，同时修掉「标题被剥离」的缺陷）；②**粗粒度**（文档级 / 上限 1500）。
- **已采纳（2026-09-20）**：正式基线 R@5 0.8167 → 0.9167（V5）；已全量重跑 baseline / 六组消融 / PDF / 简历数字，引用展示用 `body` 属性剥前缀防污染。粗粒度（V6，0.8333）因与 V5 组合不叠加、未采纳。
