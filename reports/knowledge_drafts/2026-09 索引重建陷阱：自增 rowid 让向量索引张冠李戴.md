# 索引重建陷阱：自增 rowid 让向量索引“张冠李戴”

> **核心观点**：把向量矩阵和“位置性 ID”绑定是静默事故的温床。检索质量可以毫无报错地从 0.82 跌到 0.52——因为没有任何一步“看起来失败”。

## 事故经过（VaultMind，2026-09-17）

1. 用户在知识库正常新增 9 篇笔记（系统设计上就该支持库持续增长）。
2. 重建索引（一条命令，正常成功，1.7s）。
3. 检索质量崩塌：Recall@5 0.8167→0.5167、MRR 0.7010→0.2925、坏例 11→29。
4. **没有任何报错**——唯一的异常信号是平均延迟 0.866s→0.264s（向量路实际上已经废了）。

## 根因链

- `chunks.id` 用 SQLite 自增 rowid——**位置性 ID**，行号 = 插入顺序。
- 向量索引产物是 `embeddings.npy`（N×1024）+ `chunk_ids.json`（行号→chunk id）。
- Vault 中插入新文件 → 排序后的文档顺序变化 → 后续所有 chunk 的 rowid 整体错位。
- 旧 npy 里的向量按旧行号对齐 → 每个向量都指向了**错误的内容** → 检索结果全是垃圾，但 API 正常返回 200。

## 坑位清单

| 坑 | 教训 |
|---|---|
| 静默退化 | 比崩溃更危险：没有 exception，评测数字是唯一哨兵 |
| 断点续跑 = 雪上加霜 | resume 只按 id 去重；id 是整数，错位后 id 集合看起来完全“正常”，续跑会把错映射固化 |
| 测试自己就是污染源 | 冒烟测试全管道重建真实索引库 → 每次 pytest 都改生产状态（连带删向量） |

## 修复模式（可复用）

1. **重建即失效**：rebuild 真实库时同步删除向量产物 + 醒目提示（两步命令显式化）。
2. **读时一致性闸门**：加载向量索引时校验 id 映射与库内 chunk 行号逐位一致，不一致抛错——宁可 500 不给脏答案。
3. **测试隔离**：全管道测试用临时库，测试绝不碰生产索引。
4. **长期正解**：chunk 用**内容哈希 ID**（内容→ID 稳定），重索引不再错位，向量可增量构建、评测数字位级可复现。

> 关联：{{draft-note}} 检测信号 = 评测数字漂移 + 延迟异常下降（向量路失效时 hybrid 退化到 BM25，反而变快）。
