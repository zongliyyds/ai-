# 切块别拿标题当分隔符：被剥离的标题 + 没进索引的前缀

## 核心观点

结构化切块常以 `## 标题` 作**分隔符**——副作用是**标题文本被剥离出正文块**。若标题只被写进某个「元数据字段」，而这个字段**没有进入 FTS tokens / 向量输入**，那么「裸标题查询」（只含标题词、不含正文词的问句）在索引里**没有任何字面锚点**，必然漏召。

**设计意图 ≠ 实现事实**：声称「注入了元数据前缀」不等于它真的参与了检索。

## 症状（怎么认出来）

- 分层指标撕裂：easy 题（题面含文档名）≈97%，hard 题（裸标题型）≈58%。
- 查询侧怎么救都没用：改写（-0.017 / -0.067）、标题加权重排（hard 档更差）全部无效 —— **因为问题不在查询侧**。

## 三步诊断法

1. **分层看**：按「题面是否含文档名/正文词」分层；若 hard 显著低，先怀疑索引侧缺信号，而不是查询侧不会问。
2. **指纹对照**：构造「有前缀 / 无前缀」两个索引变体，对**实际进入检索的文本**（`text`，而不是 `prefix` 字段）算 SHA-256。**指纹相同 ⇒ 前缀根本没进检索**（VaultMind 实测两变体指纹同为 `10991152b928`）。
3. **读切块代码**：确认标题是被 `split` 正则吃掉了，还是留在正文里。

## 修法与实测收益（VaultMind / 168 篇笔记 / 60 条 gold）

| 变体 | R@5 | MRR | hard R@5 |
|---|---|---|---|
| 基线（h2/600，前缀仅存字段） | 0.8167 | 0.7099 | 0.5833 |
| **前缀并入索引文本**（inline） | **0.9167** | **0.8311** | **0.7917** |
| 粗粒度（文档级/1500，前缀仍仅存字段） | 0.8500 | 0.7656 | 0.6250 |
| 细粒度（h3/300） | 0.7833 | 0.6931 | 0.5000 |

- 修法：`chunk.text = 前缀 + "\n" + 正文`（前缀含 文档标题 + 章节标题 + 标签）。
- **粒度不是越细越好**：同一语料下细粒度 **-0.0333**、粗粒度 **+0.0333**。
- **两个正因子不叠加**：粗粒度 + 前缀入检索 = 0.8333 < 只上前缀 0.9167。

## 配套坑位

- bge-m3 经 Ollama 默认 `num_ctx=4096`，单块超上下文直接 `HTTP 400 the input length exceeds the context length` → 粗粒度上限取 ~1500 中文字符；**别为迁就它调大 num_ctx**（会让变体间嵌入配置不一致，破坏单一变量原则）。
- 改索引务必隔离：临时 `db_path`/`npy_path`/`ids_path`，并加探针断言正式向量产物的 (exists, size, mtime) 未变。

## 一句话面试口径

「裸标题查询答不好，根因不在查询侧——是切块把 H2 标题当分隔符剥掉了，而标题只存在不参与检索的 prefix 字段里；把前缀真正并入索引后 R@5 从 0.817 到 0.917，hard 档从 0.583 到 0.792。」
