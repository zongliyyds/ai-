# 检索模式选择：弱路融合会稀释强路信号

## 核心观点

「混合检索一定比单路好」是直觉，不是规律。RRF 融合是**双刃剑**：当一路信号极强、另一路明显较弱时，融合会把强路的顶部排名稀释给弱路，结果**融合反而不如强单路**。用哪个模式，要让消融数据说话，而不是默认"融合更高级"。

## 现象（VaultMind 2026-09-20 实战）

做「前缀入检索」（V5）后重跑六组消融，三路单拆结果是：

| 变体 | R@5 | R@1 |
|---|---|---|
| **BM25 单路** | **0.9333** | **0.8167** |
| vector 单路 | 0.8500 | 0.7000 |
| hybrid（RRF 融合） | 0.9167 | 0.7833 |

- 前缀并入 FTS 后，BM25 拿到了「文档标题 + 章节标题」的**字面锚点**，对裸标题查询一击即中，单路全面最强。
- 而 vector 路较弱（0.85），RRF 把 bm25 的强顶部信号和 vector 的弱信号平均 → hybrid（0.9167）**低于** bm25（0.9333），融合反成拖累。

## 做法

1. **用消融定模式**：三路单拆（bm25 / vector / hybrid）是必做实验；结论看数据，不看直觉。
2. **性能最优的做默认，弱路做可选兜底**：正式管道默认 `bm25`（R@5 最高、延迟 3ms），`hybrid`/`vector` 保留为 `--mode` 可选——不删能力，只改默认。
3. **诚实标注边界**：bm25 是关键词匹配，对「同义词/换说法」类查询可能漏召回；vector 的价值恰在语义召回。默认 bm25 不代表 vector 无用，而是"默认场景下 bm25 最优、特殊场景可切"。
4. **融合增益要动态判断**：消融结论里「融合正/负增益」不要硬编码成"一定正"，要按「hybrid vs 最强单路」动态算（本项目的 `m6_ablation` 模板曾硬编码"hybrid R@1 低于 vector"导致 V5 后结论失真，已改动态对比最强单路）。

## 一句话总结

**融合是手段不是目的**：哪路最强让消融说，最强的做默认、弱的做兜底；「混合检索」是能力，不是必须上线的默认。
